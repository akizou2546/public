# 仕様書: Claude Code devcontainer × OWASP Agentic Top 10 スライド

作成日: 2026-10-04

## 1. 目的と範囲

- 目的: 技術の素養がある管理職への現状共有。決定は求めない
- 内容: 承認済みの文書「Claude Code devcontainerリファレンス実装とOWASP Agentic Top 10」と同じ判定と事実
- 範囲: リファレンス実装の3ファイルに限定する
- 書かないもの: 対策の提案、Claude Codeの他機能、人の承認を守りとする主張、組織固有の前提、発表者ノート、アニメーション

## 2. 成果物

| 成果物 | 内容 |
|---|---|
| `deck.pptx` | 編集可能なPowerPoint。Marpの編集可能方式で変換し、補正と標準グラフの差し込みを行ったもの |
| `deck.pdf` | レビュー用。完成した `deck.pptx` から作る |

進め方は2段階とする。

1. サンプル: 2〜6枚目の5枚を作り、利用者の確認を受ける
2. 残り: 確認後に1枚目と7〜15枚目を作る

## 3. スライドの型

- 大きさ: 16:9（1280×720px、PowerPoint上は960×540pt）
- 上段: メインメッセージ（1文）
- 下段: 根拠1〜2個。各「根拠のメッセージ（1文）」と、その下の図解・表・グラフ。根拠が1つなら横幅いっぱい、2つなら左右に並べる
- 左下: 章の名前とページ番号

## 4. 文章の決まり

- メインメッセージと根拠のメッセージは常体の文で言い切る。体言止めにしない
- 句点（。）は表紙から末尾まで一切付けない
- メインメッセージは32字以内で1行に収める
- つながり: 前のスライドのメインメッセージに出た単語を、次のスライドのメインメッセージが受ける。太字や「次へ」などの目印は付けない
- 説明は図解・表・グラフで行い、言葉はラベルに限る（1つ10字前後まで）
- 文になるのはメインメッセージと根拠のメッセージだけ。注記が必要なときだけ補足を1行置く
- 図や表の中の文字も1行に収める（変換後に文字枠が行ごとに分かれるため）

## 7. 作成の仕組み

| ファイル | 役割 |
|---|---|
| `deck.md` | Marpの原稿。スライドの内容はここだけに書く |
| `theme.css` | 見た目 |
| `icons/` | 使うアイコンだけを置く |
| `charts.json` | 標準グラフの数値と位置 |
| `fix.py` | 変換後の補正と検査 |
| `build.sh` | 全工程を1回で実行する |

工程: 原稿 → Marpで編集可能PowerPointへ変換 → 部首用の文字を通常の漢字へ戻す → フォント名を Noto Sans JP に直す → 標準グラフを差し込む → 検査 → PowerPointからPDFを作る

原稿のグラフ位置は空の枠にしておき、PowerPoint側でそこに標準グラフを置く。

### 検査（1つでも外れたら失敗させる）

- 12pt未満の文字がない（標準グラフの文字を含む）
- 句点（。）がない
- 部首用の文字（U+2E80〜U+2FDF）が残っていない
- メインメッセージが32字以内（表紙と出典を除く）
- フォント名が Noto Sans JP だけである
- 全ページを画像にして、崩れを目で確認する

## 8. 既知の制約

- 文字枠は行ごとに分かれる。PowerPointで書き換えても自動で折り返さない
- 図形は自由図形になり、PowerPoint標準の四角や矢印にはならない
- 英数字の前後に小さな隙間が入る
- Noto Sans JP が入っていないパソコンでは別のフォントに置き換わる。PDFはフォントを埋め込むので影響を受けない
- 表示の確認はLibreOfficeで行う。実物のPowerPointでの表示は利用者が確認する

## 9. 改訂（サンプル確認後、2026-10-04）

この節は上の節より優先する。

- 型: 最上段にタイトル（何の話かを示す短い名前）を置き、その下にメインメッセージを置く。青い下線はタイトルの下。左下はページ番号だけにする
- 文字の大きさ: タイトル36px（27pt、最大）、メインメッセージ28px（21pt）、根拠のメッセージ24px（18pt）、ラベル20px（15pt）、補足とページ番号16px（12pt）。3枚目の攻撃イメージ図の中だけはラベルも16px（12pt）
- 原稿の書き方: タイトルは `# `、メインメッセージは `## `、根拠のメッセージは `<h3>`。32字以内の決まりはメインメッセージに掛かる
- 空白: まず事実として示せる中身を図に足す。それでも空くスライドは、文字の大きさを変えずに箱と絵を大きくし、図が枠の高さの7割以上を占めるようにする
- 3枚目: 標準グラフと根拠「直接効くのは1項目だけである」をやめる。OWASP原典の「Agentic Top 10 At A Glance」をアイコンと矢印で描き直し、10項目の札を判定の色で塗り分け、右に項目名の一覧を添える。根拠のメッセージは「効くのは1項目で5項目は一部、4項目は範囲外である」の1つ。図の下に出典とライセンス（CC BY-SA 4.0）を書く
- 13枚目の標準グラフの要否は、残りのスライドを作る前に利用者に確認する
- フォント: ビルド環境に Noto Sans JP を入れてからPDFを作る。検査に「PDFに埋め込まれたフォントが Noto Sans JP だけである」を加える
- 矢印: 箱と箱の間に矢印の絵を置かず、箱の縁から縁までつなぐ線で描く。分かれ道は幹から枝を出す。遮断は点線にして途中に遮断の印を置く

## 10. 読み手が初見で読めるための決まり（2026-10-04 追加）

サンプルへの指摘を一般化したもの。全スライドに適用する。

### 10.1 初めて出る言葉と数は、先に示す

- 資料に固有の用語、略語、番号、数（「10のリスク」「ASI01」「4つの防御」など）は、初めて出るスライドか、それより前のスライドで、何を指すかを示す
- 数を言うときは、何の数かを必ず添える（「10項目」ではなく「10のリスク」）
- 番号や略語だけを単独で置かない。図の札のように場所が狭いときは、同じスライド内に名前の一覧を置く
- 説明なしに使ってよいのは、読者（技術の素養がある管理職）が知っている一般の用語だけ

### 10.2 評価や分類の言葉は、言葉だけで意味が通じるものにする

- 評価の言葉は「何が、何に対して、どうするのか」が語から読み取れるものにする
- 初めて出るスライドで定義を示す
- 以後は同じ語だけを使い、言い換えない
- 色とアイコンを必ず添える

この資料の判定語は次の3つとする（従来の「効く」「一部効く」「範囲外」を置き換える）

| 範囲を狭める | 経路は残るが被害の範囲は狭まる | オレンジ、半円 |
| 対象外 | そのリスクを対象にしていない | グレー、マイナス |

## 11. スライド作成の一般ルール（2026-10-04、サンプル承認時点のまとめ）

この資料に限らず使える形に一般化したもの。9節と10節の個別の決定は、このルールの適用例である。

### 構成

1. 冒頭に前提のスライドを置き、資料に固有の用語と数が何を指すかを先に示す
2. サマリは目次ではなく、要点を文で並べた一覧にする。要点ごとに章の名前の札を添え、その下に続く詳細スライドのタイトルを並べる
3. 各章の最初のスライドを要点のスライドとし、そのメインメッセージはサマリの要点と一字一句同じにする。詳細スライドはその直後に置く
4. 全スライドの右上に章の一覧を置き、いまの章だけを強調する。章の名前はサマリと同じ語を使う
5. 番号で構造を示さない。対応は「同じ文」と「同じ章の名前」で示す
6. 全体をPREP（要点、理由、具体例、要点）の形にする。冒頭のサマリで要点を示し、各章の要点のスライドと詳細スライドで理由と具体例を示し、末尾の「まとめ」でサマリと同じ要点を一字一句同じ文で繰り返す

### 1枚の型

1. 上からタイトル（最大の文字）、メインメッセージ、根拠1〜2個の順に置く
2. 根拠は「根拠のメッセージ（文）」と、それを説明する図解・表の組にする
3. 前のスライドのメインメッセージに出た言葉を、次のメインメッセージが受ける。目印は付けない

### 言葉

1. メインメッセージと根拠のメッセージは常体の文で言い切る。体言止めにしない。句点は付けない
2. 説明は図解と表で行い、言葉はラベルに限る
3. 数には何の数かを添える。番号や略語を単独で置かない
4. 評価や分類の言葉は、定義なしで通じる日常の語を選ぶ。等号や注記で定義しない。定義が要る語は、語そのものを替える
5. 評価の言葉は一度決めたら言い換えない。色とアイコンを必ず添える

### 図

1. 矢印は箱の縁から縁までつなぐ線で描く。分かれ道は幹から枝を出し、遮断は点線と遮断の印で示す

### 「防ぐ」から「被害を抑える」へ（2026-10-04 追加）

- 経緯: 4つの防御は、リスクが起きること自体は止めず、起きたときに被害が広がる先を絞る。OWASP も対策を「防止と低減」に呼び分けており、コンテナでの隔離は低減に当たる。「防ぐ」の物差しが合っていなかった
- 判定は2つ: 被害を抑えられる（6つ。ASI02、03、04、05、08、10）／抑えられない（4つ）。印は、抑えられるを緑のチェック、抑えられないを灰色にする
- 表の列名は「被害が出る構成」。「そのまま使うと」の欄は「抑えられる／被害が出る／起きない」
- 表紙の題: Claude Codeのdevcontainerで被害を抑えられるリスク
- 全体のメッセージ: 4つの防御で被害を抑えられるのは6つで、残りは使い方で抑える
- 要点: 結論「4つの防御はリスクを防がず、6つのリスクの被害を抑える」／判定「境界で被害を抑えられるのは6つで、4つは抑えられない」／弱点「抑えられないリスクのほかに持ち出しの経路など10の弱点が残る」／使い方「被害が出る構成を避ければ持ち出しの経路があっても被害は抑えられる」
- 「想定外のコード実行」のスライドは消す（防げる実例として置いていたので役目がなくなった）。全18枚
- 残す「防ぐ」: 8枚目（許可リストの書き換えを実際に止める話）、14枚目（公式の説明が「防がない」と書いている箇所）
- 一般ルール: 判定の物差し（防ぐのか、減らすのか、見つけるのか）を先に決める。判定の1つが0件になったら、物差しが合っているかを疑う
- 「そのまま使うと」の欄は「当てはまる／当てはまらない」の1組にそろえる（隣の列の構成に当てはまるかだけを言う）。「抑えられる」「被害が出る」「起きない」を混ぜない
- 一般ルール: 表の1つの列に入れる値は、同じ物差しの1組の言葉にそろえる
- 11枚目のメッセージ: 被害を抑えられる6つも、コンテナの中にあるものは守れない（「内側での悪用は残る」は、誰が何を悪用するのかが読み取れなかった）
- 12枚目のメッセージ: コンテナの中の判断と過信に関わる4つは抑えられない（前の文の「コンテナの中」を受ける）
- ASI05 の被害が出る構成: 成果物をホストで動かす（「ホストで実行する」は、何を実行するのかが抜けていた）。避け方は「成果物はコンテナの中で動かす」
- 一般ルール: 構成や行動を言う短い句には、何を、どこで、どうするかのうち、抜けると意味が通らないものを必ず入れる
- 全体のメッセージ（3、18枚目）: 4つの防御に加えて使い方を守れば、10のリスクの被害を抑えられる。「残りは使い方で抑える」は、使い方が効くのが4つだけに読めて、10すべてに避け方を示す16枚目と合わなかった
- 一般ルール: 全体のメッセージは、各章の要点と1つずつ突き合わせて、どれとも食い違わないことを確かめる

## ISMSの言葉に合わせる

資料全体の言葉を、ISMS（JIS Q 27000 系）の用語にそろえた。

| これまで | ISMSの言葉 |
|---|---|
| 防御 | 管理策 |
| 被害を抑えられる／抑えられない | （リスクを）低減できる／低減できない |
| 起きることは止めない | 起こりやすさは変えない |
| 弱点、脆弱性 | ぜい弱性 |
| 被害が出る構成 | 残留リスクが大きい構成 |
| 避け方 | リスク対応 |
| 判定 | 有効性 |

- 章の名前は「結論／管理策／有効性／ぜい弱性／リスク対応」
- OWASP のリスク名に含まれる語も同じ表記にする（ASI04 供給網のぜい弱性）
- 公式の文言をなぞる箇所（「使い方に3つの条件」「持ち出しは防げない」）と「守れない」は、そのまま残した
- 32文字に収めるため、4枚目は「10のうち」、14枚目は「4つの」を削った

根拠にしたもの：JIS Q 27000:2019 の転載サイト、JIPDEC の ISMS ユーザーズガイド（JIS Q 27001:2023 対応）、日本規格協会が公開する JIS Q 27002:2024 の目次（「ぜい弱性」の表記）。JIS の本体は閲覧に登録が要り、確かめていない。

一般化：読み手の分野に規格の用語があるときは、資料全体をその用語にそろえる。一部だけ替えない。引用する名前の中の語も表記を合わせる。

## 16枚目のメッセージ

- 「構成を選べば」は、何をするのかが分からないのでやめた

- 結びはISMSの「低減」にする。どの構成かは表の列（残留リスクが大きい構成）に任せる

一般化：規格の用語にそろえた資料では、日常の動詞が規格の別の用語と重ならないかを確かめる。
