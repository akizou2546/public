# 読み手から組み立てるスライド資料

## 中心の考え

資料は「読み手が何を知らず、読んだ後に何をするか」から組み立てる。手元の材料の順に並べない。
全部を作ってから見せない。少数のサンプルで型を決め、指摘は決まりに直して全体へ掛ける。

急ぎの依頼でも手順は同じ。型を決めずに全枚を作ると、指摘のたびに全枚を直すことになり、かえって遅い。

## 流れ

各段は、前の段の承認を得てから進む。承認の前に次の段の成果物を作らない。

| 段 | やること | 次へ進む条件 |
|---|---|---|
| 1 意図を聞く | 規模を声に出して分類する（試作／範囲の決まった作業／構成から決める作業）。質問は1通に1つ、選択肢を付け、おすすめを先頭に置く | 下の「聞くこと」が埋まった |
| 2 設計を見せる | アウトライン（章、各スライドのタイトルとメインメッセージ）と見た目の方針を示す | 利用者の承認 |
| 3 記録する | 設計書と実行計画をファイルに書く | 書いた |
| 4 サンプル | 型の違う5枚ほど（表紙、サマリ、図のスライド、表のスライド、まとめ）を最終の形式で作る | 利用者の確認 |
| 5 指摘を決まりにする | 下の「指摘の受け方」 | 指摘が止まった |
| 6 全枚を作る | 決まりに沿って残りを作る | 検査に合格 |
| 7 検査する | 自動検査、言葉の受け渡し、リンク先の確認、全ページを画像にして目で確認、読み手の環境で確認 | 5つとも済み |
| 8 報告する | 下の「完了の報告」 | — |

### 聞くこと（段1）

1通に1つずつ。材料から読み取れるものは聞かずに「こう読み取った」と添える。

1. 読み手は誰で、題材をどこまで知っているか
2. 読んだ後に読み手に何をしてほしいか（知る／判断する／動く）
3. 納品の形式と、読み手が開く環境（OS、アプリ、フォントの有無）
4. 見た目の基準。既定は下の「見た目」（デジタル庁デザインシステム）。会社の雛形があるかだけ聞く
5. 進め方（先にサンプルを見るか）— おすすめは「サンプルを先に」

最初の返信に書くのは、分類、読み取ったこと、最初の質問1つだけ。構成案や枚数を先に決めて書かない。

### 質問するなと言われたとき

利用者が「質問は要らない」「そのまま出して」と明言したとき、または利用者が不在のときは、聞かない。置いた前提を先頭に1〜3行で書き、下の「資料の型」「1枚の型」どおりに最後まで作る。「急ぎ」と言われただけでは、これに当たらない。

## 資料の型

| 順 | スライド | 中身 |
|---|---|---|
| 1 | 表紙 | タイトル、氏名、日付だけ。タイトルは結論の範囲を言う。ここで使った対象の呼び名を、本文でもそのまま使う |
| 2 | 目的 | 何を、どうやって確かめたか。確かめ方の限界（試していないこと）もここ。後のスライドで使う言葉と数を、ここで全部出す（「7つの観点」と書くなら、7つを先に見せる） |
| 3 | まとめ | 要点の文の一覧。章ごとに1文、その下に続く詳細スライドの名前。各要点は、その章の頭のスライドのメインメッセージと同じ文にする。メインメッセージは全部の要点を覆い、どの要点とも食い違わない |
| 4〜 | 章 | 下の「章の流れ」の順。章の頭に要点のスライド、続けて詳細。右上に章の一覧を置き、いまの章を強調する |
| 終わりの前 | 使い方 | 読み手が何をすればよいか。問題を挙げただけで終えない。基準の項目すべてに、行動を1つずつ対応させる |
| 終わり | まとめ | 3枚目と同じ題、同じメインメッセージ、同じ要点の文（PREP） |
| 最後 | 参考文献 | 文献だけ。下の「引用と参考文献」の書き方で、番号順に並べる。確かめ方の限界は混ぜず、2枚目に置く |

章の数え方や件数を数字で言ったら、その内訳が必ず別のスライドにある状態にする。
性質の違うものを1枚にまとめない（文献と限界、判定と対策など）。

## 章の流れ

何かを基準に照らして調べた・評価した資料は、この5章を既定にする。結論を先に言い、仕組み、内訳、残る課題、読み手の行動の順に進む。章の名前は題材の言葉に替えてよいが、答える問いと順番は保つ。

| 章 | 答える問い | 置くスライド | 例（Dev Containerを10のリスクに照らした資料。読み手に合わせてISMSの言葉を使い、章の名前は 結論／管理策／有効性／ぜい弱性／リスク対応） |
|---|---|---|---|
| 結論 | 結局どうだったか | 結果の全体像の図、基準と対象の対応表 | 10のリスクと管理策の有効性、リスクと管理策の対応 |
| 仕組み | 対象はどう働くか | 要点（全体の配置図）、要素ごとに1枚 | 4つの管理策の配置、通信の許可リスト、非root実行、ファイルの隔離 |
| 判定 | なぜその結果になるか | 要点（区分の内訳）、区分ごとに1枚（同じ列の表）、作り手や第三者の見解 | 有効性の内訳、低減できる6つのリスク、低減できない4つのリスク、公式の警告 |
| 残る課題 | 結果の外に何が残るか | 一覧（種類に分ける）、最も重い1つの掘り下げ | 管理策に残る10のぜい弱性、持ち出しの経路 |
| 使い方 | 読み手は何をすればよいか | 項目ごとに課題と行動を1対1で並べた表 | 残留リスクへの対応 |

- 全体のメインメッセージは、結果と行動の両方を覆う（例: 10のリスクは、4つの管理策に追加のリスク対応を重ねれば低減できる）。各章の要点と1つずつ突き合わせ、「残りは〜で」のように一部の章と食い違う言い方をしない
- 同じ種類の説明は同じ章にまとめる。1枚だけ別扱いにする理由がなくなったスライドは消す
- 題材が評価でないとき（提案、進捗の報告など）は、この表を当てはめず、問いの並びを利用者と決める

### 判定の物差し

- 判定の物差しを最初に決める。対象がしているのは、防ぐことか、リスクを減らすことか、見つけることか。物差しが合わないと、判定の言葉が全部ずれる
- 判定の1つが0件になったら、物差しが合っているかを疑う（例: 「防げる」が0件 → 対象は防ぐのではなくリスクを低減するものだった → 「低減できる／低減できない」の2つに改める）
- 「なし」「すべて」のような言い切りは、同じ資料のほかのスライドと、基準にした文書の定義に照らして確かめてから書く
- 基準にする文書の項目名と定義は、原文を本文で読んで突き合わせる。要約や記憶で訳さない。似た名前の別の文書でないかも確かめる

## 1枚の型

表紙と参考文献を除くどのスライドも、次の欄を全部埋める。埋まらない欄があるなら、スライドを分けるか統合する。表紙と参考文献にはメッセージの欄を置かない。

```
# タイトル（何の話か。体言止め。文字は一番大きい）
## メインメッセージ（言いたいこと1文。32字まで。半角の英数字は半分に数える）
### 根拠のメッセージ（1つか2つ。それぞれ1文）
　 根拠ごとに、図か表を1つ。文章の箇条書きで説明しない
```

- タイトルは体言止めにする（「残留リスクに対応する」ではなく「残留リスクへの対応」）
- メッセージの文は常体で言い切る。体言止めにしない。句点「。」は付けない
- 文は「何が、何を、どうする」の順で言う。名詞を「の」で重ねた固まりを主語にしない。名詞で終わる説明にしない。同じ語を1文で繰り返さない
- 他動詞を使うときは、目的語が文の中にあるかを確かめる（「4つの管理策で隔離する」は、何を何から隔離するのかが抜けている）
- 前のスライドのメインメッセージに出た言葉を、次のメインメッセージの頭で受ける。文の途中や終わりに同じ言葉があるだけでは、つながって読めない。「次に〜を見る」のようなつなぎの文は書かない

```
6: 4つの管理策は、ホストとの境界と外部との境界に2つずつ置かれる
7: 外部との境界では、通信を許可リストにある宛先だけに絞る
8: 許可リストは、一般ユーザーで動かすので書き換えられない
9: 一般ユーザーには、ホストとの境界で作業フォルダだけを見せる
```

- 文を1つ言い換えたら、前後の文とのつながりを通しで確かめ直す。1枚ずつの読みやすさだけで決めない
- 同じことを指す動詞は、題、メインメッセージ、次のスライドで同じにする（題が「管理策に残る10のぜい弱性」なら、メッセージも「ある」ではなく「残る」、次も「経路が残っても」）
- 根拠のメッセージは、その図や表から読み取れることを、数えられる形で言う（例: どのリスクにも残留リスクが大きい構成が1つずつある）。図にない働きや結論を入れない（図が4つの名前を並べているだけなら「4つの管理策を備える」）。ほかのスライドのメインメッセージの言い直しにしない
- 図や表と同じ内容を、文で繰り返さない
- 補足の小さい灰色の文字は置かない。要るなら図か表に入れ、要らないなら消す

## 引用と参考文献（Scienceの書き方に合わせる）

- 引用の番号は、その文献が初めて出る根拠のメッセージの末尾に、上付きで1回だけ付ける（`<sup>1</sup>`）。同じ文献を後でまた使っても付けない。全ページに番号が並ぶと、どれが何の根拠かがかえって読み取れない
- 資料全体の対象になる文献は、2枚目（目的）で付く
- 番号は初めて出た順に振り、参考文献は番号順に並べる
- 文献は「著者（組織）, 題名, 掲載元 (年); URL」の形で書く。報告書は題名を引用符でくくる。URLをリンクにする。閲覧日は書かず、版が決まるものは版（commitなど）を書く。著者名は文献の表紙どおりに書く
- 図を借りたときは、出典と利用条件をその文献の項に注として添える
- 引用した番号はすべて参考文献にあり、参考文献はすべてどこかで1回引用されている状態にする

```
1. OWASP Gen AI Security Project - Agentic Security Initiative,
   "OWASP Top 10 for Agentic Applications for 2026" (2025);
   genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/
2. Anthropic, claude-code: .devcontainer, commit 1c229fc (2026);
   github.com/anthropics/claude-code/tree/main/.devcontainer
```

## 言葉

- 判定や区分の言葉は、定義を読まなくても意味が通じるものを選び、全体で固定する（例: 低減できる／低減できない）。「＝」で定義を添えて済ませない
- 固有名は、初めて出るスライドの図の中で、何者かを一言添える（例: OWASP の箱に「ソフトウェアの安全に取り組む非営利団体」）
- 同じものを別の名前で呼ばない。表紙の題で使った呼び名を、本文でもそのまま使う
- 製品や仕組みの名前は、作り手の公式の書き方を確かめてから書く。大文字小文字や分かち書きは利用者に確かめる
- 「一部」「条件付き」と言うときは、どの条件で外れるかを同じ行に書く
- 構成や行動を言う短い句には、何を、どこで、どうするかのうち、抜けると意味が通らないものを必ず入れる（「ホストで実行する」ではなく「成果物をホストで動かす」）
- 「最小にする」「適切に」「穴」のような、程度だけの言葉やたとえは、何がどうなのかを言う言葉に直す
- 利用者の言い回しをそのまま採らない。誤解を招かないか、言い方を複数並べて選んでもらう
- 確かめていない話は載せない。載せるか迷ったら利用者に聞く
- 読み手を不安にさせる事実を載せたら、どうすればよいかを必ず対にする

### 規格の用語に合わせるとき

読み手の分野に規格の用語があるとき（ISMS など）は、次のとおりにする。

- 資料全体をその用語にそろえる。一部だけ替えない。章の名前、題、表の列、区分の言葉まで替える（例: 防御→管理策、弱点→ぜい弱性、被害を抑えられる→低減できる、被害が出る構成→残留リスクが大きい構成、避け方→リスク対応、判定→有効性）
- 引用する項目名の中の語も、同じ表記にする（「供給網の脆弱性」ではなく「供給網のぜい弱性」）
- 日常の動詞が、規格の別の用語と重ならないかを確かめる（ISMSの「回避」は「低減」とは別の選択肢なので、低減の話で「避ければよい」と書かない）
- 作り手や公式の文言をなぞる箇所は、無理に替えない。替えなかった箇所は報告する
- 用語は規格の本体で確かめる。本体を読めなかったときは、何を根拠にしたか（解説書、目次、転載など）を設計書に書き、「未確認」と報告する
- 替えた後は、32字の上限と枠の幅を検査し直す。用語が長くなって収まらない文は、削った語を報告する

## 図と表

- 矢印は箱の縁から箱の縁までつなぐ。箱の間に浮かせない
- 数を比べる意味のないグラフは描かない。関係は図、対応は表で見せる
- 続けて出る表は、列の構成と幅を同じにする
- 表の1つの列に入れる値は、同じ物差しの1組の言葉にそろえる（「当てはまる／当てはまらない」に、「起きない」「低減できる」を混ぜない）
- 文字は12pt以上。ページ番号は右下
- 色だけで意味を伝えない。判定の色には、言葉かアイコンを必ず添える
- 空白が目立つときは、文字を足さず、箱と絵を大きくする

## 指摘の受け方（段5）

指摘1つごとに、この順で行う。

1. **意味が1つに定まらない指摘は、直す前に聞く。** 「フォントがおかしい」「イメージと違う」では原因が分からない。何が、どのアプリで、どう見えているかを1つ質問する。推測でフォントや構成を変えない
2. **決まりに直す。** 「2枚目の『7つの観点』が唐突」→「言葉と数は、使う前のスライドで出す」
3. **設計書の決まりの一覧に書き足す。**
4. **全スライドに掛ける。** 指摘された箇所だけでなく、同じ決まりに反する箇所を全部直す
5. **返信に、足した決まりと直した箇所を書く。**

サンプルへの指摘が片付く前に、残りのスライドを作らない。

## 付属ファイル

このスキルのフォルダ（Claude Code では `${CLAUDE_SKILL_DIR}`）に、次のファイルが付いている。あるときは作り直さずに使う。ないとき（SKILL.md だけで使う環境）は、下の「変換」の記述から同じものを作る。

| ファイル | 使い方 |
|---|---|
| `tools/theme.css` | 見た目のテーマ。資料のフォルダに写して使う。値は下の「見た目」と同じ |

## 変換（Marp → 編集できるPowerPoint）

```bash
CHROME_NO_SANDBOX=1 timeout 120 marp deck.md --no-stdin --theme-set theme.css --html \
  --allow-local-files --pptx --pptx-editable -o raw.pptx
soffice --headless --convert-to pdf deck.pptx   # 確認用のPDFは、補正後のPowerPointから作る
pdftoppm -r 80 -png deck.pdf page                # 全ページを画像にして目で見る
```

| 症状 | 原因 | 対処 |
|---|---|---|
| 変換が終わらない | 標準入力を原稿として待っている | `--no-stdin` |
| 漢字が似た別の文字になる | 部首用の文字（U+2E80〜U+2FDF）に化ける | `<a:t>` の中のその範囲だけNFKCで直す |
| フォント名がばらばら、校正が中国語 | 変換時の名前のまま | `typeface` を本来の名前に、`lang` を `ja-JP` に書き換える |
| PDFだけ字形が違う | 作業環境にそのフォントがない | フォントを入れ、`pdffonts` で確かめる |
| 横に並べた見出しや表のセルが1つの箱にまとまってずれる | 間が1.5字分より狭い | 間を1.5em以上あける。表は列の幅を決め打ちし、足りなければ文字を18pxまで下げる |
| 文字が枠からはみ出す | PowerPoint側では英数字の前後に空きが入り、HTMLより幅が広がる | 幅に1割の余裕を見る。長い名前は行を分ける |
| 読み手のパソコンで文字化けする | 読み手にそのフォントがない | 下のとおり埋め込む |
| リンクが消える | 変換でリンクは落ち、文字は複数の区切りに分かれる | 原稿の `<a href>` の文字と続きの区切りを突き合わせ、各区切りの `<a:rPr>` に `u="sng"` と `<a:hlinkClick r:id>` を足し、スライドの関係ファイルに外部リンクを足す。テーマの `hlink` の色も主色にする。戻せなかったリンクは検査で落とす |
| 確認用のPDFでリンクの色が抜ける | リンクの後ろに、同じ行で別の文字が続いている | リンクは行の最後に置く |
| 引用の番号が文に重なる | 番号は別の箱になり、PowerPoint側で文の幅が変わる | 番号の箱を消し、同じ行で左隣の根拠のメッセージの末尾に `baseline="30000"` の区切りとしてつなぐ。上付きは約6割に縮むので `sz` は2100（12pt相当）。横線は U+2012 に変わるので、そろえて比べる |

### フォントの埋め込み

名前の指定だけでは、読み手のパソコンにフォントがないと化ける。4つとも要る。

1. TTFをEOT 2.2（版 `0x00020002`、フラグ0、圧縮なし）に包み、`ppt/fonts/fontN.fntdata` として入れる
2. `[Content_Types].xml` に `<Default Extension="fntdata" ContentType="application/x-fontdata"/>`
3. `ppt/_rels/presentation.xml.rels` にフォントへの関係、`ppt/presentation.xml` の `<p:notesSz>` の後ろに `<p:embeddedFontLst>`（`typeface`、`panose`、`charset="-128"`、標準と太字）
4. `<p:presentation>` に `embedTrueTypeFonts="1" saveSubsetFonts="1"`。ないと埋め込んでも使われない。同じ属性が2つあるとファイルが開けないので、消してから足す

```python
def eot(ttf_path):
    import struct
    from fontTools.ttLib import TTFont
    data, font = open(ttf_path, "rb").read(), TTFont(ttf_path)
    os2, p = font["OS/2"], font["OS/2"].panose
    head = struct.pack("<II", 0x00020002, 0) + bytes([
        p.bFamilyType, p.bSerifStyle, p.bWeight, p.bProportion, p.bContrast,
        p.bStrokeVariation, p.bArmStyle, p.bLetterForm, p.bMidline, p.bXHeight])
    head += struct.pack("<BBIHH", 1, os2.fsSelection & 1, os2.usWeightClass, os2.fsType, 0x504C)
    head += struct.pack("<6I", os2.ulUnicodeRange1, os2.ulUnicodeRange2, os2.ulUnicodeRange3,
                        os2.ulUnicodeRange4, getattr(os2, "ulCodePageRange1", 0), getattr(os2, "ulCodePageRange2", 0))
    head += struct.pack("<5I", font["head"].checkSumAdjustment, 0, 0, 0, 0)
    for name_id in (1, 2, 5, 4):  # ファミリー名、スタイル名、版、完全名
        text = (font["name"].getDebugName(name_id) or "").encode("utf-16-le")
        head += struct.pack("<HH", 0, len(text)) + text
    head += struct.pack("<HH", 0, 0) + struct.pack("<IIHHII", 0, 0, 0, 0, 0, 0)
    return struct.pack("<II", 8 + len(head) + len(data), len(data)) + head + data
```

## 検査（段7）

5つとも済むまで「完成」と言わない。

- **自動検査**: 12pt未満、句点、部首用の文字、指定外のフォント名、フォントの埋め込み、メインメッセージ32字超（半角の英数字は半分に数える）、PDFの埋め込みフォント、原稿のリンクが全部ファイルに入っているか、引用と参考文献の番号が対応しているか（引用にない文献、文献にない引用、初めて出た順）
- **言葉の受け渡し**: メインメッセージを順に並べて読み、どの文も前の文の言葉を頭で受けているかを確かめる
- **リンク先**: 組み上げたファイルからリンクを取り出し、1つずつ開いて、ページの見出しがリンクの文字と合うかを確かめる。開けなかったものは「未確認」と報告する
- **目で見る**: 全ページの画像を開き、はみ出し、重なり、つながっていない矢印、ずれた見出しを探す。文や表を直したら、そのページを必ず見直す
- **読み手の環境**: 自分の環境で崩れないことは、読み手の環境で崩れない根拠にならない。フォントを埋め込んだうえで、読み手のアプリで開いた結果を利用者に確かめてもらう。まだなら「未確認」と報告する

## 完了の報告（段8）

次の4つの欄を、この順で書く。

1. 渡すファイル
2. 確かめたこと（何で確かめたか）
3. 確かめていないこと（読み手の環境での表示、開けなかったリンク、推測で埋めた箇所はスライド番号つき）
4. 自分の判断で決めたこと（戻せる形で）
